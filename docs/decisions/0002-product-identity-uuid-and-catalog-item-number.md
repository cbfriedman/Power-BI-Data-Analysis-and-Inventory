# 0002. Product identity: internal UUID with Catalog Item Number as business key

- **Status:** Accepted
- **Date:** 2026-09-07

## Context

The Nineyard Catalog Item Number is the primary business reference for a product
and is how humans and upstream systems refer to it. It is also an *external*
identifier: Nineyard controls its format, its stability, and its lifecycle. A
supplier-controlled string is a poor primary key — if it is ever reformatted,
reissued, merged, or corrected upstream, every foreign key referencing it breaks
or, worse, silently points at the wrong product.

Separately, one Catalog Item may carry multiple Amazon SKUs, so any model that
assumes one identifier per product is wrong from the start.

## Decision

- Every product has an immutable internal `UUID` primary key, generated by this
  system and never reused or changed.
- `nineyard_catalog_item_number` is a separate, uniquely constrained column — a
  business attribute, not a key.
- **All** foreign keys target the UUID. No foreign key anywhere references a
  Catalog Item Number, vendor SKU, UPC, or any other external string.
- Additional identifiers (UPC, EAN, GTIN, MPN, ASIN) live in a one-to-many
  `product_identifier` table, storing both raw and normalized values.
- Amazon SKUs live in a one-to-many `amazon_sku` table.
- Products are soft-deactivated, never hard-deleted, so historical mappings and
  import rows stay interpretable.

## Alternatives considered

| Option | Why not |
|---|---|
| Catalog Item Number as the primary key | Couples the whole schema to an external system's key policy; an upstream correction becomes a cascading migration |
| Integer surrogate key | Works, but leaks record counts, complicates future merges across environments, and the brief requires UUIDs |
| Single `upc` column on `product` | Cannot represent products with several identifiers, or the raw-vs-normalized distinction that matching needs |

## Consequences

**Positive** — upstream identifier changes become a single-column update.
Multiple identifiers and multiple Amazon SKUs are representable. Match rules can
compare normalized values without losing the original.

**Negative** — every product lookup by Catalog Item Number needs an index and one
extra hop; UUID keys are wider than integers, which costs some index size. Both
are acceptable at this data volume.
